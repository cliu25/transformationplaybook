Deep Dive

Systems Integration

Most AI projects don't fail because the model isn't good enough. They fail because the data pipeline breaks, the integration is too brittle to scale, or no one knows how to maintain it after the build team leaves. This chapter walks through how to surface integration complexity early, write requirements developers can actually build from, and hand off a solution that survives the transition to production.

Active across Engage → Discover → Execute
Engage · Systems Integration Tech & Data Assessment

Know what you're working with before you commit.

By the time you're ready to assess integration readiness, you need an honest picture of two things: what systems you have, and what condition the data is in. The Technology & Data Assessment in Engage is where you surface the constraints that will shape every decision downstream. Without it, you're designing solutions for an architecture that doesn't exist and building on data that isn't ready.

The goal here is not to fix anything — it's to document what's real. Map your systems of record: where does the data live, who owns it, what format is it in, and what's required to access it? For each system, confirm whether APIs exist, whether they're documented, and whether you have the permissions to use them. If the answer to any of those is no, that's not a blocker — it's information. It tells you where the integration work will be heavy and where you'll need architectural review.

The systems landscape shows what you're integrating with. Each source system needs to be assessed for API availability, data quality, access permissions, and ownership. The integration layer is where most of the hidden work lives.
⚠ Pain point
Assuming data is ready because it exists
The most common mistake in this phase is treating "we have the data" as equivalent to "the data is usable." Data that exists in a system is not the same as data that's clean, accessible, documented, and in a format your pipeline can consume. Run a data quality profile on a sample: check for nulls, duplicates, format inconsistencies, and missing values. If 30% of your key fields are empty or malformed, that's not a problem you discover during the build — it's a constraint you document now and plan around.

Also confirm who owns each system and what the process is for getting access. If you need to go through an Architecture Review Board (ARB) or security review to connect to a system, that timeline needs to be visible now — not when the build team is waiting for credentials. The output of this assessment is a checklist: for each system, you know whether it's ready to integrate with, what work is required to make it ready, and who needs to approve that work.

⚠ Pain point
Skipping technical discovery to 'save time'
When timelines are tight, teams skip the technical assessment and go straight to design. The logic is: "We'll figure out the integration details during the build." This guarantees delays. Integration complexity that surfaces mid-build stops forward progress while the team scrambles to understand systems they should have mapped weeks earlier. The assessment takes two weeks. The delay from skipping it costs two months. Do the assessment.
1
Map all source systems — CRM, ERP, document repos, legacy apps. Document what data lives where.
2
Check API availability for each system. If no API exists, document the alternative access method (file export, database query, etc.).
3
Profile data quality on a sample from each source. Check for nulls, duplicates, format issues, and missing values.
4
Identify access requirements — who owns each system, what approvals are needed, what the timeline is for getting credentials.
5
Flag ARB or security review needs early. If architectural approval is required, start that process now.

Discover · Systems Integration Step 2 · Workflow Analysis · Solution Design

Map the technical landscape and make the build-vs-buy call.

Discover has two integration jobs. First, during Workflow Analysis, you document the as-is technical architecture for the workflow you're transforming — what systems are involved, how data flows between them, and where the bottlenecks are. Second, during Solution Design, you make the build-vs-buy decision for each integration point and write requirements that are specific enough for a developer to build from without asking clarifying questions.

Step 3

Workflow Analysis — Document the technical baseline

The Workflow Analysis is where you map the current technical architecture in detail. For the workflow you're transforming, trace the data flow: where does it originate, what systems does it pass through, what transformations happen along the way, and where does it end up? Document every integration point, every manual handoff, and every place where data quality degrades. This map becomes the reference for understanding what you're replacing and what you need to preserve.

Also identify the non-functional requirements that will constrain your design: ARB approval timelines, security review requirements, data residency rules, and compliance constraints. These aren't nice-to-know details — they're hard gates that will block your build if you don't plan for them. If your solution needs to pass through ARB, that review takes 4-6 weeks. If you discover that in week eight of a 12-week build, you've just missed your delivery date.

The current-state flow shows where manual work, delays, and errors occur. The future-state flow shows what you're building to replace it. Both maps are required — one tells you what you're fixing, the other tells you what success looks like.
⚠ Pain point
Underestimating integration complexity
Integration work is consistently underestimated because it's invisible until you start building. A system that "has an API" might have an API that's undocumented, rate-limited, or missing the fields you need. A data source that "is accessible" might require a VPN, a service account, and three levels of approval to actually connect to. Map the integration complexity in detail during Workflow Analysis — not as an optimistic estimate, but as a realistic accounting of every step required to move data from source to solution.

Step 4

Solution Design — Write build-ready requirements

With the technical baseline documented, Solution Design is where you make the build-vs-buy decision for each integration point and write requirements specific enough for a developer to act on. The build-vs-buy decision is not about what's technically possible — it's about what's strategically worth building. Use a simple framework: if the integration is unique to your workflow and core to your competitive advantage, build it. If it's a commodity capability that others have solved, buy or reuse an existing connector.

The build-vs-buy matrix helps you decide where to invest custom development effort. Build what's strategically valuable and technically simple. Buy or partner for everything else. Document the decision and the reasoning — you'll need to defend it later.

Once you've made the build-vs-buy call, write the requirements. This is where most handoffs fail: business teams write requirements that make sense internally but are too conceptual for a development team to build from. The test is simple: give a developer the requirements document and ask if they can write a user story from it without asking you a single question. If they can't, it's not ready.

Build-ready requirements include: the persona (who is using this), the data objects (what fields, what format, what source system), the systems involved (what APIs, what authentication, what error handling), the acceptance criteria (what does done look like), and the fallback path (what happens when the integration fails). If any of those are missing or vague, the developer will stop and ask — and that's when your timeline slips.

⚠ Pain point
Requirements 'too conceptual to build from'
This is the most common handoff failure in the entire process. Business teams write requirements like "integrate with CRM to pull customer data" — which sounds clear but leaves a developer with twenty questions: which CRM? Which API endpoint? Which fields? What format? What happens if the API is down? What's the authentication method? Build-ready requirements answer all of those questions before the developer asks them. If your requirements document is under three pages, it's probably too conceptual. Add specificity until a developer can start building without a clarification call.
1
Map the current-state architecture for the workflow you're transforming. Document every system, integration point, and data flow.
2
Identify ARB and security review requirements early. Start those processes immediately — they take 4-6 weeks.
3
Make the build-vs-buy decision for each integration point using the matrix. Document the reasoning.
4
Write build-ready requirements with persona, data objects, systems, APIs, authentication, error handling, acceptance criteria, and fallback paths.
5
Test the requirements by giving them to a developer. If they need to ask clarifying questions, add more specificity.
6
Document the tech stack decision with pros, cons, and tradeoffs. You'll need to defend it when questions arise later.

Case StudyState University — Build-vs-buy decision

For the document verification workflow, the team faced three integration points: CRM data pull, document storage access, and ERP update. They used the matrix: CRM integration was high-value, low-complexity (existing Salesforce connector) — buy and customize. Document storage was high-value, high-complexity (custom mainframe interface) — partner with IT to build. ERP update was low-value, high-complexity — descoped to post-MVP. The team documented each decision with reasoning, which proved critical when the CFO questioned why they weren't integrating with ERP in the first release.

Execute · Systems Integration Experimentation · Scale & Adopt

Build, integrate, instrument, and hand off cleanly.

Execute is where integration theory meets reality. The requirements you wrote in Discover get tested against actual systems, actual data, and actual failure modes. The goal is not just to build something that works in a demo — it's to build something that runs reliably in production, handles errors gracefully, and can be maintained by someone other than the person who built it.

Step 5

Experimentation — Build and validate on real data

The first job in Execute is to validate that the data you profiled in Engage is actually usable when you try to build with it. Connect to the real systems, pull real data, and run it through your pipeline. The quality issues you find here — missing fields, format inconsistencies, unexpected nulls — are not surprises. They're confirmation of what you documented earlier. The difference is that now you have to handle them in code.

Build your integrations with error handling from day one. Every API call can fail. Every data source can return unexpected formats. Every system can go down. Your code needs to handle all of those gracefully: log the error, alert the right person, and either retry or fail safely. The integrations that break in production are the ones that were built assuming everything would work perfectly.

Integration testing validates that data flows correctly from source to target through every transformation step. Test both the happy path and every failure mode — API timeouts, malformed data, authentication failures. If you haven't tested a failure scenario, it will happen in production.
⚠ Pain point
Data quality worse than expected
The data quality profile you ran in Engage was on a sample. When you connect to the full dataset in Execute, you'll find edge cases the sample didn't catch: records with all nulls, dates in unexpected formats, IDs that don't match between systems. This is normal. The mistake is treating these as blockers rather than expected work. Build your pipeline to handle bad data gracefully: log it, flag it for review, and keep processing. A pipeline that crashes on the first bad record is not production-ready.

Also instrument everything. Add logging that captures: what data came in, what transformations were applied, what went out, and whether it succeeded or failed. When something breaks in production — and it will — you need to be able to trace exactly what happened without guessing. The integrations that are easiest to maintain are the ones where every step is logged and every error is visible.

⚠ Pain point
One-off integrations that can't scale
When timelines are tight, teams build integrations that work for the MVP but can't scale to production volumes. A script that works fine for 100 records per day breaks when it hits 10,000. An API call that succeeds in testing fails in production because of rate limits. Build for scale from the start: batch processing for high volumes, rate limiting for API calls, retry logic for transient failures. The integration that works in the demo but fails at scale is worse than no integration at all — because now you've committed to a timeline you can't meet.
1
Connect to real systems and validate data quality on the full dataset, not just the sample. Document edge cases.
2
Build error handling into every integration — API timeouts, malformed data, authentication failures. Log everything.
3
Test all failure scenarios — not just the happy path. If you haven't tested it, it will break in production.
4
Instrument the pipeline with logging that captures input, transformations, output, and errors. Make failures visible.
5
Build for scale from day one — batch processing, rate limiting, retry logic. Don't wait until production to discover volume issues.

Step 6

Scale & Adopt — Hand off a maintainable solution

The handoff to production is where most integrations fail. Not because the code doesn't work — but because no one knows how to maintain it after the build team leaves. A successful handoff requires three things: complete technical documentation, a named owner who can actually run and maintain the solution, and a clear escalation path when something breaks.

The technical documentation includes: the code repository with README and test cases, the architecture diagram showing all integration points, the secrets and API keys with instructions for rotation, the data lineage documentation showing where each field comes from, and the runbook for common failure scenarios. If any of those are missing, the solution will degrade quietly until it stops working entirely.

The technical handoff checklist ensures the solution can be maintained after the build team leaves. Every item is required — not optional. A solution with incomplete documentation or no named owner will fail quietly over time.

The named owner is not just a name on paper — it's a person who has been trained on the solution, understands how it works, can troubleshoot common issues, and knows who to escalate to when they can't. If the owner can't answer basic questions about how the integration works, the handoff isn't complete. Spend time with them. Walk through the code. Run through failure scenarios. Make sure they can actually maintain what you're handing off.

⚠ Pain point
No named technical owner after handoff
The most common handoff failure is transferring the solution to "the IT team" or "the platform team" without a specific person who owns it. When something breaks, no one knows who's responsible for fixing it. The issue gets escalated, bounced between teams, and eventually the solution stops working. Avoid this by naming a specific owner before the handoff, confirming they have the skills and capacity to maintain it, and documenting their name in every piece of handoff documentation. If you can't name a person, the handoff isn't ready.
1
Complete the technical handoff checklist — code, secrets, architecture, data lineage, runbook, monitoring, owner, escalation path.
2
Name a specific technical owner who can run, maintain, and troubleshoot the solution. Not a team — a person.
3
Train the owner by walking through the code, running through failure scenarios, and confirming they can troubleshoot independently.
4
Document limitations and next steps — what's not production-ready yet, what needs to be improved, what's on the backlog.
5
Set up monitoring and alerting so failures are visible immediately. Don't wait for users to report issues.
6
Change ownership in the system — update access controls, transfer API keys, document the handoff date and new owner.

Case StudyState University — Clean handoff to IT

Before the enrollment transformation team stepped back, they completed a full technical handoff to Sarah Chen, the IT integration specialist. The handoff included: documented code repository with test cases, architecture diagram showing all three system connections, API keys with rotation procedures, data lineage documentation, and a runbook for the five most common failure scenarios. Sarah shadowed the build team for two weeks, ran through each failure scenario, and confirmed she could troubleshoot independently. Six months later, when the CRM API changed and broke the integration, Sarah diagnosed and fixed it in under two hours using the runbook — without needing to escalate to the original build team.
