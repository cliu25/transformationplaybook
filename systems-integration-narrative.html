How-to Deep Dive

Systems Integration

Most AI projects don't fail because the model isn't good enough. They fail because the data pipeline breaks, the integration is too brittle to scale, or no one knows how to maintain it after the build team leaves. This chapter covers how to surface integration complexity early, write requirements that developers can build from, navigate the path to production at IBM, and hand off a solution that survives after the sprint ends.

Active across Engage → Discovery → Execute
Engage Systems Integration Step 1 & 2 · Tech & Data Assessment

Know what you're working with before you commit.

Who to involve
Domain focal CIO/BPT architect Data or platform owner Process SMEs

The Technology and Data Assessment is where you surface the constraints that will shape every decision downstream. The goal is not to fix anything. It is to document what is real: what systems the domain runs on, where data lives, what condition it is in, and what it takes to access it. Without this picture, you design solutions for an architecture that does not exist and build on data that is not ready.

Work with the domain focal to inventory the major platforms in use, then bring in the CIO/BPT architect to validate the technical picture. For each system, confirm: Does an API exist? Is it documented? Do you have the permissions to use it? Who owns it? If the answer to any of those is no, that is information. It tells you where integration work will be heavy and where you will need architectural review before you can build anything.

IBM operates on modern enterprise platforms. The integration questions here are rarely about whether systems exist. They are about data freshness, access controls, and platform dependencies. A system that updates once a week instead of in real time shapes what your AI solution can do. A platform team that manages access to a Salesforce org or a ServiceNow environment controls your timeline. Surfacing those dependencies in Engage, not mid-build, is the entire point of this step.

IBM runs on modern enterprise platforms. The integration risk is rarely "this system is too old." It is usually access controls, data freshness, and platform team capacity. Document the constraints early so they shape the design, not stop the build.
⚠ Pain point
Assuming data is ready because it exists
The most common mistake here is treating "we have the data" as equivalent to "the data is usable." Data that exists in a platform is not the same as data that is clean, accessible, documented, and in a format your pipeline can consume. A Salesforce field that exists but updates once a week instead of in real time changes what your AI can do. A Box folder that requires a separate provisioning request changes your timeline. Run a data quality check on a real sample. If 30% of key fields are incomplete or stale, that is a constraint to plan around, not a surprise to discover in Sprint 3.

Also confirm who owns each platform and what the approval process is for accessing it. If you need to go through the Architecture Review Board (ARB) or an IBM security review to connect to a system, that timeline needs to be visible now. ARB review can take four to six weeks. If you surface that dependency in week eight of a twelve-week build, you have already missed your date. The CIO/BPT architect can tell you which systems require ARB and how to start that process. Start it before Discovery ends.

Three patterns come up consistently across IBM domains during this step. First, the platforms your solution depends on are often owned by teams outside the domain — CIO product teams, enterprise infrastructure groups, or platform owners with their own roadmaps and priorities. The solution is not to work around them. It is to identify named resources from each platform team early and bring them into the conversation. Second, API connectors for internal platforms are frequently undocumented or immature, especially for older systems. Before committing to an agentic architecture that depends on a specific integration, confirm with the CIO/BPT architect that the required API is stable, documented, and can support the call volume you need. Third, platform roadmaps are not always formalized or shared. A capability you are designing around may already be in development elsewhere, or may be on a deprecation path. Ask the architect what the roadmap looks like before you commit to it.

🔴 When to escalate
Small issues (a missing API key, an undocumented endpoint, a data format inconsistency) can be worked through with the platform team directly. Large structural blockers — a major platform migration, a multi-month security review, significant infrastructure investment — need to be escalated to the domain VP and CIO leadership before the solution design is finalized. If cross-org communication is not progressing and a platform team is unresponsive or cannot commit a named resource to your timeline, escalate to the AIFT team (Radha). Cross-org coordination at the enterprise level is part of what AIFT exists to do.

Case StudyState University: discovering the integration landscape

In week one of Engage, the enrollment team worked with the university's IT architect to map every system touched by the document verification workflow. Box was the document repository, the admissions CRM held applicant records, and a third system managed enrollment decisions. Box had a well-documented API and the team already had credentials. The CRM required a separate access request through the IT governance process. The enrollment decision system had no API at all, only a weekly batch export to a shared folder.

The team documented all three. They started the CRM access request immediately, which took two weeks to clear. The batch export on the enrollment system was flagged as a constraint: any AI that depended on real-time enrollment status would not work. That single finding changed the scope of the solution before a line of requirements was written.

Discovery Systems Integration Step 3 & 4 · Workflow Analysis · Solution Design

Map the technical baseline, make the right build decisions, and write requirements developers can act on.

Who to involve
CIO/BPT architect Product owner Domain focal Process SMEs ARB reviewers (if needed) Security team (if needed)

Discovery has two integration jobs. First, during Workflow Analysis (Step 3), you document the current-state technical architecture for the specific workflow you are transforming. Second, during Solution Design (Step 4), you make the key integration decisions and write requirements that are specific enough for a developer to build from without a clarification call.

Step 3

Workflow Analysis: document the technical baseline

For the workflow you are transforming, trace how data actually moves: where it originates, what systems it passes through, what transformations happen along the way, and where it ends up. The process SMEs tell you how the workflow runs. The CIO/BPT architect tells you how the data moves underneath it. Both views are required.

Document every integration point, every manual handoff, and every place where data quality degrades or updates are delayed. Also identify the non-functional requirements that will constrain your design: ARB approval timelines, security review requirements, data residency rules, and compliance constraints. These are hard gates. If ARB review takes four to six weeks and you discover that requirement in week eight of a twelve-week build, you have missed your delivery date.

Step 4

Solution Design: integration decisions and build-ready requirements

With the technical baseline documented, Solution Design answers two questions: what integration approach will you use for each connection point, and what exactly needs to be built? Both need to be resolved before the build team starts. A vague answer to either question means the build team will stop and ask, and that is when your timeline slips.

Build vs. buy considerations. At IBM, most AI solutions end up being built with internal development capacity using watsonx and existing API connectors. The real question is not usually "build or buy" in the traditional sense. It is whether any individual integration points have pre-built connectors available (watsonx Orchestrate has over 150 pre-built connections to Salesforce, SAP, ServiceNow, Slack, and others) and whether it makes sense to use them rather than building custom. When a pre-built connector covers 80% of what you need, configure and extend it. When the requirements are specific enough that a pre-built connector would require more customization work than building from scratch, build. Document the reasoning either way. You will need to defend the decision later.

For each integration point, decide whether to use a pre-built connector, build custom, configure quickly, or defer. Document the decision and the reasoning. At IBM, most core integrations end up built, but the Orchestrate connector catalog covers many common platforms and is worth checking first.

Write build-ready requirements. The test: give the CIO/BPT architect and the product owner the requirements document and ask whether a developer can write a user story from it without a clarification call. Build-ready requirements include the persona, the specific data objects (fields, format, source system), the systems involved (API endpoint, authentication method, rate limits), the acceptance criteria, and the fallback path when the integration fails. If any of those are missing or vague, the developer will stop and ask, and that is when your timeline slips.

⚠ Pain point
Requirements too conceptual to build from
Business teams write requirements like "integrate with the CRM to pull applicant data." That sounds complete but leaves a developer with twenty questions: which CRM object? Which fields? What authentication method? What happens if the API returns an error? What is the rate limit? Build-ready requirements answer all of those questions before the developer asks. If the product owner and the CIO/BPT architect cannot review the requirements together and confirm a developer can start without clarification, the requirements are not ready.
How to write build-ready requirements
1
Map the current-state architecture for the selected workflow with the process SMEs and CIO/BPT architect. Document every system, integration point, and data flow.
2
Check ARB and security review requirements with the architect. Start those processes immediately if needed. They take four to six weeks.
3
Check the watsonx Orchestrate connector catalog for each integration point. Use a pre-built connector where it covers 80%+ of the requirement. Build where it does not.
4
Write build-ready requirements covering persona, data objects, source systems, API details, authentication, error handling, acceptance criteria, and fallback paths.
5
Test requirements with the architect and product owner. If a developer would need to ask clarifying questions, the requirements are not ready. Add specificity until they are.
6
Document the integration approach for each connection point with reasoning. You will need to defend it when questions arise during the build.

Case StudyState University: integration decisions in Solution Design

The Workflow Analysis confirmed three integration points: the admissions CRM (applicant records), Box (document storage), and the enrollment decision system (batch export only). For the CRM, the CIO/BPT architect confirmed a documented Salesforce API was available and the access request was already in progress. For Box, a pre-built connector in the watsonx environment covered the file access pattern they needed. For the enrollment system, the batch-only limitation ruled it out for the MVP. It was explicitly moved to Wave 2.

Requirements were reviewed by the product owner and the architect together. The original requirement read "check Box for required documents." The final version specified the exact document types (transcript, government ID, personal statement), the Box folder structure, the API call pattern, the field that would be written back to the CRM on completion, and the exception path when a document failed validation. The developer started Sprint 1 without a single clarification call.

Execute Systems Integration Step 5 & 6 · Experimentation · Scale & Adopt

Build, integrate, instrument, and hand off cleanly.

Who to involve
CIO/BPT architect Developer lead Product owner Platform team (for production) Named technical owner

Execute is where integration design meets reality. The requirements you wrote in Discovery get tested against actual systems, actual data, and actual failure modes. The goal is not to build something that works in a demo. It is to build something that runs reliably in production, handles errors without manual intervention, and can be maintained by someone other than the person who built it.

Step 5

Experimentation: build and validate on real data

Connect to the real systems in Sprint 1 and run real data through the pipeline. The quality issues you find here are confirmations of what you documented in Engage, not surprises. The difference is that now you handle them in code. Build error handling from the first day: every API call can fail, every data source can return unexpected formats, and every system can go down. Your code needs to handle all of those gracefully, log the error, alert the right person, and either retry or fail safely.

Instrument everything. Set up logging and monitoring before anything goes to production. You need to know when the pipeline fails before users report it. Track API call success rates, data validation pass rates, processing times, and error frequencies. These are not just operational metrics. They are the evidence base for whether the solution is working in practice and whether it is ready to scale.

Test failure scenarios as deliberately as you test the happy path. API timeout, malformed data, authentication failure, rate limit hit, source system unavailable. If you have not tested a failure mode, it will happen in production.

Test both the happy path and every failure mode. If you have not tested a failure scenario, it will happen in production. UAT should only begin after end-to-end integration is validated on real data, not mocked data.
⚠ Pain point
Navigating delivery pressure vs. building something robust
If your team feels pressure to deliver quickly, the temptation is to skip error handling, use mocked data for testing, or defer monitoring to "after launch." Each of those shortcuts creates a production system that fails quietly and takes weeks to diagnose. The path to production at IBM runs through the CIO/BPT platform team, and they will not accept a solution without error handling and monitoring in place. Building those things correctly in Sprint 1 is faster than retrofitting them during the ARB review that will block your launch.
Navigating path to production at IBM

One of the most common points of confusion in IBM AI transformations is the path to production. The CIO/BPT organization plays two roles: they provide development resources through their architect and build capacity, and they own the platform teams that control the production environment. Your architect is a partner in building. The platform team controls whether you can deploy. These are separate conversations with separate timelines.

The key to moving through the path to production is to enable your architects to solve the right problems and the big problems rather than being pulled into delivery work that keeps them from seeing the broader picture. When architects are focused on the right problems, they can help you navigate platform requirements, anticipate ARB feedback before the formal review, and connect you to the right platform team contacts. When they are heads-down in day-to-day delivery, those strategic connections do not happen.

Practically: start the ARB process in Step 3 (Workflow Analysis), not after requirements are complete. Bring the architect to the initial steering committee meeting so the CIO organization understands the solution from the start. When you hit a platform requirement that looks like a blocker, the architect is the person who knows whether it is a real blocker or a standard process with a known path through it.

Step 6

Scale & Adopt: hand off cleanly and maintain what was built

A clean technical handoff means one specific person, not a team, takes ownership of the integration. Before the build team steps back, complete a technical handoff checklist and confirm the named owner can actually maintain what they are taking over.

The named technical owner is not just a name on paper. They need to have been trained on the solution, run through failure scenarios with the build team, and confirmed they can troubleshoot independently. If the owner cannot answer basic questions about how the integration works, the handoff is not complete.
⚠ Pain point
No named technical owner after handoff
The most common handoff failure is transferring the solution to "the IT team" or "the platform team" without a specific person who owns it. When something breaks, no one knows who is responsible. The issue gets escalated, bounced between teams, and the solution stops working. Name a specific person before the handoff. Confirm they have the skills and the capacity to maintain it. Document their name in every piece of handoff documentation. If you cannot name a person, the handoff is not ready.
How to build and hand off cleanly
1
Connect to real systems in Sprint 1. Validate real data flows through the pipeline before UAT begins. Do not use mocked data to test integration.
2
Build error handling and logging from day one. Every API call needs a failure path. Every failure needs a log entry and an alert.
3
Test every failure scenario explicitly: API timeout, malformed data, authentication failure, rate limit hit, source system unavailable.
4
Start the ARB process in Workflow Analysis and keep the CIO/BPT architect close to the build. They are the bridge to the platform team and the ARB reviewer.
5
Name a specific technical owner before the build team steps back. Not a team: a person. Walk them through the code, run through failure scenarios together.
6
Complete the technical handoff checklist before stepping back. Code access, credentials, architecture diagram, runbook, monitoring, owner name, and escalation path.

Case StudyState University: clean handoff to the IT integration team

Before the build team stepped back, they completed a full technical handoff to a named IT integration specialist. The handoff included: documented code repository with test cases, architecture diagram showing all three system connections (Salesforce CRM, Box, and the admissions decision system), API credentials with rotation procedures, data lineage documentation, and a runbook for the five most common failure scenarios. The specialist shadowed the build team for two weeks, ran through each failure scenario, and confirmed she could troubleshoot independently.

Six months later, when the Salesforce API version was deprecated and broke the integration, the specialist diagnosed and fixed it in under two hours using the runbook, without contacting the original build team. That outcome is only possible when the handoff is complete before the build team leaves.
